## P1：先保障正确性

### S01 — Rust Wayland 初始画布尺寸

- **位置**：`rust/src/wayland.rs:966`；`rust/src/app.rs:392`（`resize_screen`）。
- **触发**：初始化 `App::new(Pixmap::new(1,1), 1920,1080)`，首个 configure 恰为逻辑 1920×1080，缩放为 1。
- **问题**：`resize_screen` 因屏幕尺寸未变化直接返回；`set_scale(1)` 也不重建。应用状态说画布是全屏，但像素存储仍为 1×1，批注无法正常保存。
- **修复**：构造时让尺寸一致，或把实际 canvas 尺寸纳入重建条件。
- **验收**：1920×1080/100% 首次 configure 后 canvas 为 1920×1080；其他分辨率/125%/200% 同样满足尺寸不变量，屏幕右下角可画可撤回。

### S02 — Rust 撤回区域漏乘设备缩放

- **位置**：`rust/src/paint.rs:161,180`；`rust/src/app.rs::save_undo_rect`。
- **触发**：设备缩放大于 1，画笔或橡皮在远离原点的位置操作。
- **问题**：绘制用了 scale transform，撤回瓦片截取却使用逻辑坐标。比如逻辑 `(200,200)` 在 200% 下画到物理 `(400,400)`，保存区域仍在约 `(200,200)`。
- **修复**：统一 LogicalRect→PhysicalRect 转换；边界用向外取整，包含抗锯齿和变化笔宽。
- **验收**：100/125/150/200% 下画笔、橡皮、手掌橡皮撤回后像素与操作前一致；跨瓦片、画布边缘和曲线也覆盖。

### S03 — Rust Wayland 双缓冲写入正在使用的存储

- **位置**：`rust/src/wayland.rs:281`（`flush`）、`reconfigure`。
- **问题**：选择一个空闲 buffer 后，循环向两份 buffer 的 mmap 都写入脏区；另一份可能仍为 busy。重配置时也复用并清空旧共享存储，未等待旧 buffer release。
- **影响**：合成器读取同时被修改，可能产生撕裂、闪烁和不可预期图像；这里确认的是生命周期违反，未实测具体画面。
- **修复**：只写已 release 的 buffer；给每个 buffer 保存内容代次/待补脏区。重配置使用新 pool，并保留旧 pool 至其 buffer 全释放。
- **验收**：模拟一个 buffer 长时间 busy 时，存储内容不被写入；两个都 busy 时保留待绘内容；release 后提交最新完整帧。缩放/resize 同样验证。

协议依据：共享存储应在合成器释放后才复用，见 [Wayland wl_buffer / wl_surface 规范](https://wayland.freedesktop.org/docs/html/apa.html)。

### S04 — C++ Wayland 配置变化未重建缓冲

- **位置**：`cpp/src/backend_wayland.cpp:103,302,396`。
- **问题**：`layerConfigure` 直接改变 `width_/height_`，已有 pool 时 `maybeCreateBuffers` 不重建；fractional scale 事件也只更新系数。后续 QImage 与 damage 用新尺寸，buffer 和 mmap 仍是旧尺寸。
- **影响**：尺寸扩大时有写越界风险；缩放/resize 会错位或不清晰。没有在此环境中运行 ASan Wayland 复现。
- **修复**：configure/scale 进入统一重配置过程，检查乘法溢出和分配上限；清理旧资源按 release 生命周期执行。
- **验收**：ASan/UBSan 下重复切换 1080p/4K、100/125/200%、拔插输出，无越界；新旧缓存行为符合 S21 约定。

### S05 — 页缓存静默丢失与容量差异

- **位置**：`rust/src/app.rs:420`；`cpp/src/wps.cpp:47`；`cpp/src/backend_wayland.cpp:906`。
- **问题**：Rust/C++ X11 WPS 缓存达到 20 个有墨迹页后，新增页保存直接返回。C++ Wayland 非白板始终用 `kCacheOther=2`，联动课件仅保留两页，且空页也占缓存。
- **触发**：在 21 个课件页画笔迹后往返；C++ Wayland 则第 3 页后已可能淘汰旧页。
- **修复**：统一模式容量与字节预算；需要淘汰时使用明确的 LRU/落盘策略和用户可理解的提示，避免把最小页号当访问时间。
- **验收**：21 页/50 页有墨迹课件、10 页白板、多次往返，保留和淘汰行为一致；内存超预算不静默丢内容。

### S06 — 重复清空和全屏识别误判

- **位置**：`rust/src/main.rs::tick`；`rust/src/x11.rs:424,492`；`cpp/src/wps.cpp::wpsHandleLine/checkWpsState/isOfficeWindow`。
- **问题**：放映 Begin 和独立全屏扫描都能清空缓存；扫描结果改变时还把 `current_slide` 重置为 1。两个实现的办公软件类名匹配包含过短字符串 `et`，也会命中包含它的其他程序类名。
- **影响**：从第 N 页开始放映、延迟检测、假全屏和窗口切换可能清掉笔迹或页码；多屏几何兜底可能漏掉只占单屏的放映。
- **修复**：加载项会话在线时以其状态为权威；全屏扫描只用于降级，使用明确的类名规则和对应输出几何，按会话变更幂等清空。
- **验收**：从第 5 页开始、重复 Begin、窗口最大化/全屏切换、非 Office 类名包含 `et`、双屏放映，不产生额外 clear。

### S07 — 结束放映和重连状态分裂

- **位置**：`rust/src/wps.rs::tick/handle_line`；`rust/src/main.rs:1313`；两个 C++ 桥的 `handleLine`。
- **问题**：Rust 离线保留桥的 `real_pos`，上层却把 `wps_real_pos` 重置为 -1；同页重连不会产出 RealPos，下一次换页可能跳过保存旧页。C++ 两个桥没有完整 SlideShowEnd 分支；独立桥也没有结束回调。
- **实测**：C++ 独立桥收到 Begin(pos=3)、End、State(pos=3) 后仅有 Begin 回调，没有恢复到一个新的会话状态。
- **修复**：只由会话控制器维护权威页号，重连同步完整快照；End、离线和重新开始分别定义，不靠无关窗口扫描补足。
- **验收**：断线超过 3 秒后同页重连、换页后重连、End 后同页再开始，正确保存旧页并恢复页号，不串课件。

### S08 — 白板退出缺少状态重同步

- **位置**：Rust `wps.rs::handle_line` / `App::toggle_whiteboard`；C++ `wpsHandleLine` / `WlBackend::wpsOnRealPos`。
- **问题**：白板期间应用忽略或不应用外部事件，JS 仍更新 `_lastState`。退出白板恢复进入前页号，没有请求当前放映快照；如果外部期间换页或结束，之后没有新变化就不会重新通知。
- **修复**：白板笔迹独立保存，同时保留外部会话的最新状态；退出白板时按快照恢复。明确处理进入白板前排队的命令/End 事件。
- **验收**：白板中用键盘/鼠标换页、结束放映、开始另一课件，再退出白板，显示当前真实页对应笔迹且不清掉白板。

### S09 — JS 事件注册不幂等

- **位置**：`wps-addin/js/bridge.js::startBridge`。
- **实测**：调用两次 startBridge，6 种事件被注册为 12 个监听器，虽然 interval 仍只有一个。
- **影响**：尤其重复 SlideShowBegin 能引发多次清空；有重试或重复 onLoad 时风险增加。
- **修复**：分别记录启动、注册和重试状态；按 API 对象/生命周期清理监听器，确保最多一份。
- **验收**：调用 onLoad/startBridge 10 次、Application 延迟出现、ApiEvent 延迟出现，最终恰有 6 个监听器和一个轮询任务。

### S10 — JS 状态上报丢失和轮询生命周期缺失

- **位置**：`bridgePushIfChanged/bridgeFetch/startBridge`。
- **实测**：网络失败前已经更新 `_lastState`，同页第二次调用不重试；没有 ApiEvent 时从 pos=1→非放映→pos=1 只上报一次 State；没有完整 End/Begin 转换。
- **问题**：本地桥重启但课件页未变化时同样不会重新推送状态。多个 fetch 没有 in-flight 限制、确认序号和过期规则，结果顺序需要进一步验证。
- **诊断误导**：`OnSaPing` 没有询问HTTP健康状态，网络失败时也提示“联动桥在线”，本轮已复现。
- **修复**：区分“观察到”与“已确认”的状态；定期发送会话快照，检测放映开始/结束，失败重试，限制并发并校验序号。
- **验收**：前两次 push 失败、第 3 次恢复；无 ApiEvent 的完整放映周期；桥重启且不翻页；延迟/乱序响应，最终状态一致。

### S11 — WPS 登记存在覆盖和迁移风险

- **位置**：`wps-addin/install.sh`；Rust `ensure_addin_registered`；两个 C++ 自动登记实现。
- **实测**：已有 `other-addin` 登记后运行原安装逻辑，该条目被整文件复制覆盖。
- **代码问题**：自动登记按字符串匹配 XML；带属性的根节点可能被整体替换。Rust 删除旧登记使用整行过滤，紧凑 XML 同行的其他条目可能一起删除。C++ 遇旧名称直接返回，不规范化旧状态。
- **修复**：解析 XML，只合并/迁移本项目节点；原子写、备份、保留其他节点/属性；所有安装入口共用行为规则。
- **验收**：多加载项、紧凑 XML、根属性、旧名称、重复登记、损坏 XML和写入失败均覆盖；不损坏其他加载项。

### S12 — HTTP 会话与资源边界不足

- **位置**：三个桥的 HTTP 解析、heartbeat、队列；Rust `handle_conn/start`。
- **问题**：任意请求（包括静态文件或未知路径）算在线；无客户端/session 校验，能够访问服务的其他客户端可伪造 Begin 清缓存或取走命令。CORS 为 `*`，请求方法没有严格限制。Rust 读请求行没有长度上限，单线程串行处理慢连接，命令/事件队列无上限；Qt 连接也缺少明确超时和读大小约束。
- **边界**：服务只绑定 loopback；浏览器能否访问受其本地网络策略影响，本轮没有证明任何浏览器利用链。
- **修复**：验证预期 Host/Origin 与实际 WPS 兼容性；动态 API 加会话校验，明确握手/心跳，限制请求/连接/队列；静态资源白名单，404/405/400 区分；命令带 TTL、ID 与执行确认。新旧协议迁移见重构计划。
- **验收**：未知客户端、伪造 Begin、错误 Origin/Host、超长行、慢连接、连续 push、断线后旧命令，不能破坏正常会话或无限占内存。

### S13 — 测试误通过和用户目录副作用

- **位置**：`cpp/tests/test_bridge_api.py::run_tests`；`rust/src/wps.rs::tests::bridge_endpoints`。
- **实测**：未提供加载项目录时 `/manifest.xml` 返回 `200 OK` + `OK`；原 Python 套件仍 5/5、退出码 0。`/poll` 只查 HTTP 200，没有证明 NEXT/PREV 顺序和执行。
- **代码问题**：Rust 测试使用生产端口 16666；占用时直接 return 算成功，start 还执行用户真实登记和日志写入。
- **修复**：注入端口（0/临时端口）、注册目录、日志路径和时钟；测试启动自己的服务；解析 XML/验证内容；针对队列、状态副作用、错误码做断言，禁止静默跳过。
- **验收**：manifest 缺失、队列顺序错误、无法启动均使测试失败；整个套件不能修改真实用户登记；并行测试及生产端口占用不影响结果。

### S14 — Rust arm64 包可含错误架构

- **进度（2026-09-30）**：已修复打包前架构校验。保留容器产物优先、普通 release 兜底的选择顺序，但两条路径都必须匹配目标的 64 位小端 ELF Machine，类型为 EXEC/DYN。缺少 readelf、无法读取 ELF 头或格式不匹配时，在改动已有包与暂存目录前失败。
- **位置**：`rust/build_deb.sh` 选择 BIN 的回退逻辑。
- **触发**：amd64 开发机只有本机 release 产物，但要求打 arm64 包。
- **原问题**：脚本回退到 `target/release/sidera`，control 写 arm64，却没有检查 ELF Machine。
- **回归证据**：`rust/tests/test_build_deb.py` 的 5 组、17 个场景在 WSL Ubuntu 26.04 amd64 通过。旧脚本有 11 个拒绝场景失败；新脚本全部通过。使用真实 dpkg-deb 构包和解包，检查 control 架构、二进制内容、权限及失败时旧产物保留；已加入现有 CI。
- **剩余验收**：测试使用 ELF 元数据夹具，没有编译/运行真实 Rust arm64 应用；最低 ABI、构建元数据和对应架构上的安装启动仍按 S22/S23 与发布计划执行。
- **验收**：上述触发必须失败；两种架构包中的 ELF、control、文件路径一致，并在对应架构启动。

## P2：兼容、维护与发布

### S15 — C++ 独立桥启停漏停定时器

`WpsBridge::start` 创建以桥为 parent 的 QTimer，`stop` 仅把指针置空，没有 stop/delete。探针三次启动、两次停止后有 **3 个活动定时器**。修复所有权和停止顺序，释放已接受连接；验收 100 次启停后只有 0/1 个活动 timer，关闭后没有连接或回调残留。X11 旧桥 timer 的 parent 不同，不应直接套用同一实测结论。

### S16 — 截图剪贴板持续性与 Wayland 支持

`rust/src/main.rs:438` 的 Clipboard 是局部变量，set_image 后立即 drop；Cargo 中 arboard 没启用 `wayland-data-control`。Linux 剪贴板对象销毁后内容可能不可用，具体结果受剪贴板管理器影响；见锁定版本的 [arboard 3.6.1 Clipboard 文档](https://docs.rs/arboard/3.6.1/arboard/struct.Clipboard.html) 和 [Linux 后端说明](https://docs.rs/arboard/3.6.1/arboard/index.html)。C++ Wayland 使用 Qt offscreen 平台，`setImage` 是否能把内容送到真实桌面也需要验证。修复为长期存活的剪贴板服务及明确平台实现；在无剪贴板管理器、纯 Wayland/有 XWayland 下分别粘贴到 WPS 和图像应用。

### S17 — Portal 截图请求生命周期

`rust/src/portal.rs` 先调用 Screenshot，再订阅 Response，存在快速响应早于订阅的竞态；没有超时、取消或并发上限。file URI 仅去掉前缀，含转义字符的路径不能保证读取成功。按 handle_token 提前订阅并处理超时/取消，用 URI 解析；见 [Portal Request 规范](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Request.html)。验收响应在调用完成前后到达、用户取消、服务缺失、带空格路径和连点截图；所有任务能结束并给出准确反馈。

### S18 — 能力差异没有产品化表达

Rust `WlPlat::screenshot` 总返回 None（实际全走 Portal），`virtual_right_click` 为空，`is_presentation_fullscreen` 总 false；C++ Wayland 缺少 uinput/Portal 回退、全局热键和 X11 同等手掌橡皮。两者都要求 layer-shell，uinput 不解决缺失该协议的覆盖层。引入能力探测和 Result 返回，禁用不可用动作并解释原因；验收每个平台上诊断、按钮状态、实际行为一致，启动失败不能当正常成功退出。

### S19 — 输出、seat 与版本协商

C++ `registryGlobal` 忽略服务器公告 version，直接 bind output=4、seat=7、layer-shell=4 等；较低公告版本时有协议错误风险，且提前获取 pointer/touch，未按 capability 变化处理。Rust 输出新增/更新/移除回调为空，只有一个 overlay；C++ 使用首个 output、忽略移除。修复版本取 min、capability 生命周期和每输出状态，处理整数缩放与 viewport 缺失路径。验收旧协议模拟器、无触摸 seat、热插拔、主屏切换、旋转和混合 DPI；双屏支持范围明确。

### S20 — 触摸取消与停留

Rust `TouchHandler::cancel` 仅清 App 手势，未清 Ip touch IDs/UI 标记；1.5 秒无事件的兜底会把持续按住但静止的触点判作异常，可能提前解除鼠标抑制。`gesture::touch_event` 起笔画点后未设置 dirty，静止落笔可能延迟到下一事件才显示；shape 常晚于 down，需要按帧聚合。C++ Wayland shape/cancel 为 no-op、只跟踪单 touch。建立 Begin/Frame/Cancel 规则；验收静止按住 3 秒、首触即时反馈、丢 End、Cancel、多指切换、手掌 shape 与鼠标合成抑制。

### S21 — 显示变化与旧缓存

Rust set_scale/resize 清掉当前画布，却保留旧尺寸 slide/whiteboard cache；load_page 直接把旧 Pixmap 作为新 canvas 使用。X11 初始化时固定根几何，没有完整 RandR 更新流程；C++ primaryScreen 与多屏坐标也不统一。需要定义重采样/保留逻辑尺寸/明确丢弃的策略，在缓存中记录 geometry 与 scale。验收投影仪插拔、分辨率切换和缩放后返回旧页，笔迹位置、撤回和输入区保持一致或有明确可接受提示。

### S22 — 可复现构建不足

一键脚本需要仓库外提供 `amd64-sysroot/`、`aarch64-sysroot/`，没有可用的初始化脚本、来源或校验；Rust 依赖可变 stable 工具链，容器 build 没有 `--locked`。Makefile 可选 Wayland 检测未同时检查 xkbcommon；产物功能由环境隐式决定。没有 `.gitattributes`，当前 Windows 检出为 CRLF，直接交给 Bash 会失败。补可重建/可校验环境、固定工具链、显式后端选项、LF 属性和配置变更后的干净构建；验收两种架构从干净检出可重现，缺依赖有清楚错误，产物记录编译能力。

### S23 — 包依赖与兼容门禁

C++ 本轮 ELF 直接链接 Qt5Network，但两个 DEB Depends 未声明对应运行库；若编入 Wayland，libwayland-client/libxkbcommon 也应纳入。现代宿主构建不能证明 glibc/Qt5.12 兼容；Rust 声明 libc6>=2.30 也需用实际产物检查。用 [dpkg-shlibdeps](https://manpages.debian.org/trixie/dpkg-dev/dpkg-shlibdeps.1.en.html) 从目标产物生成依赖，在最低支持环境验证；控制文件、安装/升级/两版替换/卸载、udev 生效、desktop 和图标都进入测试，禁止把本轮宿主文件发布为低 ABI 包。

### S24 — 配置、字体、单实例和失败反馈

配置写入是直接覆盖且很多错误被忽略；路径硬编码家目录，与 XDG 自启动路径不完全一致。Rust 解析 `sbScale` 时未明确拒绝 NaN；Fonts 只载排序后的最多 3 个可解析字体，未验证中文覆盖；现有字体测试用中英混合字符串的总非透明像素断言，英文可见不能证明中文可见。自启动固定 `Exec=sidera`，源码运行时可能无法自启动。Rust 单实例探测/删除/绑定存在竞争窗口，失败返回 None 后正常退出；不同语言单实例名也不同，且Rust主事件循环接收唤醒连接后无超时read可被空连接阻塞。引入带默认值/有限值校验的 Config、原子保存、中文字形覆盖检测、明确可执行文件策略和实例锁/非阻塞唤醒。验收损坏配置、只读目录、缺中文字体、源码启动、并发双启动、空连接和跨实现启动；错误能准确显示。

### S25 — 性能、内存与时钟

Rust X11 4ms 轮询、定时同步遍历窗口树；WPS 日志与部分文件操作同步发生；左右侧栏脏区合并成跨屏包围盒会扩大重绘。按页数限制不能控制 4K 缓存内存，C++ 全屏撤回复制也需量化。多数时长/心跳用墙上时钟，系统时间调整会扰动超时；Rust UI 保留整笔 stroke_pts/commit 路径但当前交互主要用增量绘制，相关测试覆盖不同路径。以实测决定优化，持续时长用单调时钟，限制内存/日志/线程，明确真实绘制路径；验收指标见测试环境。

### S26 — 重复业务和隐含所有权

Rust main/App/UI 相互引用，C++ 全局 g 与裸指针遍布，多套页缓存/HTTP/配置/触摸语义各自演化。将状态、输入、绘图、协议、平台与 IO 拆分，C++ 两个后端共用 PageStore/PresentationController/WpsBridge；Rust 抽出可独立测试的 core。通过共享行为 fixture 检验两个实现，不以文件拆小本身作为验收；具体步骤见重构计划。

### S27 — CI、文档与元数据

`custom` push 不触发 CI；C++ 无接口/Wayland构建测试；没有 arm64、包安装和实机门禁。README 说“通吃/生产”、Rust 有 screencopy 回退等，与能力和测试证据不一致；桥注释仍有“默认假键”而实现已入队。版本散落代码和脚本；Cargo `GPL-3.0-only` 与 LICENSE 的“v3 或后续版本”表述不一致，需要作者明确许可意图并统一元数据。补 CI 矩阵和测试证明，把支持范围、启动顺序、已知限制写清，版本从单一来源生成；本轮不擅自变更许可或删除版本。

### S28 — 编译打包安装后应用图标不显示

- **状态与现象**：用户反馈编译并安装后看不到应用图标，列为待修复。具体发行版、桌面、安装包版本、C++/Rust 实现以及缺失位置（应用菜单、任务栏或程序内部）尚未记录；本轮未在目标桌面复现，不能认定某一打包字段就是根因。
- **位置**：`cpp/build_deb_amd64.sh`、`cpp/build_deb_aarch64.sh`、`rust/build_deb.sh`；程序内部资源加载另见 `cpp/src/drawing.cpp::sideraIconPath`、`rust/src/main.rs::load_icon`。
- **已确认的现状**：三个打包脚本都复制 SVG 到 hicolor 和 pixmaps，复制 PNG 到 hicolor 的 256×256 目录，桌面入口使用 `Icon=/usr/share/pixmaps/sidera.svg`。因此不能仅凭脚本推断“没打包图标”；需要检查实际发布包。程序内部的 PNG 加载与桌面入口图标是不同路径，源码目录中的资源也可能掩盖安装后的资源问题。绝对路径写法本身不足以证明缺陷。
- **排查与修复**：先记录故障位置和目标桌面，在不依赖源码目录的新测试用户下安装实际 DEB；核对包内容、安装路径、权限、图像解码和 desktop 字段。根据复现结果统一图标名称、资源安装位置与入口生成；若是任务栏/窗口图标缺失，检查对应后端的应用身份与 desktop 关联。核实目标发行版的图标缓存及软件包触发器，确有缺口时补安装/升级/卸载处理，不以用户手工复制图标作为最终方案。
- **验收**：两种实现、两种发布架构在各自声明支持的桌面上，全新安装、覆盖升级、卸载重装后，应用菜单/启动器显示正确图标且能启动；设为收藏后图标保持正确。对本来应显示在任务栏的窗口检查图标与分组；覆盖层刻意不出现在任务栏时记为不适用。程序设置/启动画面的图标也应正常，不依赖当前工作目录或 `SIDERA_ICON`。无需用户手动补资源或刷新缓存；保存安装包校验和、桌面版本和截图，按 G22 记录结果。
